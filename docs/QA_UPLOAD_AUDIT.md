## Pipeline Architecture

The upload pipeline is well-structured in `server/src/services/pipeline/` with clean separation:

1. **Entry**: `POST /api/statements/upload` → `StatementService.upload()` → `PipelineService.processStatement()`
2. **Text extraction**: `text-extraction.ts` — pdf-parse with 3× retry + exponential backoff
3. **Account detection**: `account-detection.ts` — parser-first, AI fallback, auto-create accounts
4. **Bank parsing**: `bank-parser.ts` → `parserRegistry` (8 banks: CBA, ANZ, Westpac, NAB, StGeorge, Bendigo, ING, Macquarie)
5. **AI fallback**: `ai-parsing.ts` — Claude agent orchestrator → legacy AI → vision verification
6. **Categorization**: `categorization.ts` — AI with merchant memory + GST inference
7. **Finalization**: `pipeline-finalize.ts` — insert transactions, link accounts, index Cognee, detect transfers
8. **Batch**: `POST /api/batch-uploads` → `BulkUploadQueue` with worker pool + persistence

## CRITICAL Issues

### C1. Statement ID mismatch — uploaded statement uses wrong ID for pipeline processing
**File**: `server/src/services/statements/statement-service.ts:24-40`
**Severity**: CRITICAL

The `upload()` method generates a local `id = crypto.randomUUID()` on line 24, but passes the statement data to `statementRepository.create()` on line 31 **without including the `id`**. The repository's `create()` method (statement-repository.ts:28) generates its **own** `randomUUID()` internally.

This means:
- `pipeline.processStatement(id, filePath)` on line 40 uses the **locally generated ID**
- The database record has a **different ID** (generated by the repository)
- The pipeline looks up the statement by ID (`db.select().from(statements).where(eq(statements.id, statementId))` in pipeline.ts:21) — **this lookup will return no results**
- The pipeline proceeds with `stmt = undefined`, so `userId` is undefined
- All subsequent operations (account detection, transaction linking, user settings) are broken
- The `events.emit('update', { type: 'statement_added', id })` on line 39 references the wrong ID

**Impact**: Every single-file upload silently fails to link to the correct statement record. Transactions may still be inserted (pipeline continues despite `stmt` being undefined) but with no `userId`, no account linking, and no user-specific categorization.

```typescript
// statement-service.ts:31 — id is NOT passed to create()
await statementRepository.create({
  filename: file.name,    // ← no `id` field!
  hash,
  uploadDate: new Date().toISOString(),
  parsingStatus: 'PENDING',
  userId,
});

// statement-repository.ts:28 — generates its OWN id
async create(data: { ... }) {
  const id = randomUUID();  // ← different UUID!
  await insert(db, statements, { id, ...data });
}
```

**Fix**: Pass `id` to `statementRepository.create()`:
```typescript
await statementRepository.create({ id, filename: file.name, hash, ... });
```
Or change repository to accept an optional `id` parameter.

### C2. No file type validation on upload endpoint
**File**: `server/src/routes/statements.ts:30-45`
**Severity**: CRITICAL

The upload route accepts **any file type** without validation. There is no check for:
- MIME type (should accept `application/pdf`, `text/csv`, `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`)
- File extension
- File size limits

A user could upload a `.exe`, `.zip`, or 10GB file and it would be written to disk and passed to `pdf-parse`, which would either crash or produce garbage.

```typescript
// statements.ts:33 — no type/size check
const file = body['file'];
if (!file || !(file instanceof File))
  return c.json({ error: 'No file provided' }, 400);
// Immediately proceeds to upload — no validation!
const result = await statementService.upload(getUserId(c), file);
```

**Fix**: Add file type + size validation before processing.

### C3. `transactionHash` has no unique constraint in schema
**File**: `server/src/schema/transactions.ts:32`
**Severity**: CRITICAL

The `transactionHash` column is defined as `text('transaction_hash')` with **no unique constraint and no index**. While the application code does manual dedup checks (categorization.ts:144-160), this is:
1. **Race-condition vulnerable**: Two concurrent pipeline runs for the same statement could both pass the "existing" check and insert duplicates
2. **Not enforced at DB level**: Any direct SQL insert bypasses the application-level check
3. **Missing index**: The `WHERE transaction_hash = ?` queries do a full table scan

**Fix**: Add `unique()` constraint or at minimum an index on `transactionHash`.

## HIGH Issues

### H1. CSV/XLS parsers exist but are NOT wired into the upload pipeline
**Files**: `server/src/services/parsers/formats/csv-parser.ts`, `server/src/services/parsers/formats/ofx-parser.ts`, `server/src/services/parsers/formats/qif-parser.ts`
**Severity**: HIGH

Libraries are installed (`csv-parse`, `exceljs` in package.json) and full parsers exist:
- `CSVStatementParser` with multi-bank config detection
- OFX parser with date/amount handling
- QIF parser with multiple date formats

However, the upload pipeline in `pipeline.ts` only calls `extractPdfText()` (pdf-parse). There is **no code path** for CSV, XLS, OFX, or QIF files. If a user uploads a CSV, the pipeline will:
1. Try to parse it as PDF → fail
2. Set status to `FAILED` with `PDF_READ_ERROR`

The batch upload queue (`job-processor.ts:130`) also only calls `pipeline.processStatement()` which only handles PDFs.

**Fix**: Add file-type detection at the start of `processStatement()` and route to the appropriate parser.

### H2. Agent insertion path missing GST fields
**File**: `server/src/services/pipeline/agent-insertion.ts:36-57`
**Severity**: HIGH

When transactions go through the Claude agent path (`handleAgentPathInsertion`), the insert records are missing `gstAmount` and `gstCategory` fields that the regular path (`prepareTransactionInserts` in categorization.ts:113-127) correctly computes. This means:
- Agent-path transactions have `gstApplicable` set but no `gstAmount` or `gstCategory`
- BAS calculations that rely on `gstAmount` will show $0 GST for these transactions
- Business credit card auto-GST flagging doesn't apply on the agent path

**Fix**: Add GST calculation to agent-insertion.ts using `inferGstCategory()` and `calculateGstAmount()`.

### H3. Batch upload queue processes ALL files as PDFs
**File**: `server/src/services/queue/job-processor.ts:130`
**Severity**: HIGH

The batch upload queue accepts any files via `POST /api/batch-uploads` but processes every single one through `pipeline.processStatement()`, which assumes PDF input. The batch endpoint collects files as buffers (batch-uploads.ts:31) and writes them to disk, but the processing pipeline only does `extractPdfText()`.

**Fix**: Detect file type from extension/MIME and route to appropriate parser in the queue processor.

### H4. `pipeline.processStatement()` is fire-and-forget in single upload
**File**: `server/src/services/statements/statement-service.ts:40`
**Severity**: HIGH

The `upload()` method calls `pipeline.processStatement(id, filePath)` **without `await`**. This means:
1. The function returns `{ id, message: 'Started' }` immediately
2. Any unhandled rejection in the pipeline is silently swallowed (no `.catch()`)
3. The client has no way to know if processing actually started

While this is intentional for async processing, there's no `.catch()` on the promise:
```typescript
pipeline.processStatement(id, filePath);  // ← no await, no .catch()
```

The batch queue (`job-processor.ts:130`) correctly `await`s the pipeline call.

**Fix**: Add `.catch()` to log errors, or use the batch queue pattern.

## MEDIUM Issues

### M1. Non-CBA bank parsers are scaffolds, not production-grade
**Files**: `server/src/services/parsers/banks/anz.ts`, `westpac.ts`, `nab.ts`, etc.
**Severity**: MEDIUM

The CBA parser (364 lines) has sophisticated multi-line transaction handling, balance continuity correction, and CBA-specific amount parsing. The other 7 parsers (ANZ, Westpac, NAB, StGeorge, Bendigo, ING, Macquarie) use a generic regex approach that:
- Relies on simple line-by-line matching (`DD MMM YYYY Description Amount Balance`)
- Doesn't handle multi-line transactions
- Doesn't handle bank-specific concatenated amount formats
- Has no balance continuity correction

These will likely produce poor results on real statements from those banks, causing fallback to AI parsing (which works but is slower and costs money).

### M2. Reprocess doesn't validate file still exists before starting
**File**: `server/src/services/statements/statement-service.ts:54-58`
**Severity**: MEDIUM

The `reprocess()` method scans the upload directory looking for a file that starts with `statementId`. Given the C1 bug (statement ID mismatch), this lookup will **never find the file** because the disk filename uses the locally-generated ID but the DB stores a different ID.

Even without C1, if the file was deleted from disk, the `readdir` + `find` approach is fragile. The file path should be stored in the statement record.

### M3. Gap analysis is a stub
**File**: `server/src/services/statements/statement-service.ts:67-74`
**Severity**: MEDIUM

The `getGapAnalysis()` method only returns `{ totalStatements: completedStmts.length }`. It doesn't actually analyze gaps between statement periods, which is the stated purpose of the endpoint. A real gap analysis would:
- Sort statements by period dates
- Find missing months/periods between consecutive statements
- Report uncovered date ranges

### M4. Vision verification stores results in wrong field
**File**: `server/src/services/pipeline/ai-parsing.ts:152-153`
**Severity**: MEDIUM

The vision verification results are stored in the `validationErrors` column:
```typescript
.set({ validationErrors: visionVerification })
```

This column name implies it contains errors, but it's being used to store verification metadata (counts, discrepancy percentage, review flag). This is semantically confusing and could lead to the statement appearing as having errors when it's actually just metadata.

### M5. Transfer detection uses `parseInt(id)` on UUID strings
**File**: `server/src/services/pipeline/transfer-detection.ts:69-71`
**Severity**: MEDIUM

```typescript
const candidates: TransferCandidate[] = allUserTxs.map((t) => ({
  id: parseInt(t.id as string, 10) || 0,  // ← UUIDs parse to NaN → 0
  accountId: parseInt((t.accountId as string) || '0', 10) || 0,
```

Transaction and account IDs are UUIDs (e.g., `"a1b2c3d4-..."`) but `TransferCandidate.id` expects numbers. `parseInt()` on a UUID returns `NaN`, which falls back to `0`. This means **every transaction gets `id: 0`** and **every account gets `accountId: 0`**, making transfer detection useless — all transactions appear to be from the same account with the same ID.

## Statement Status Tracking

Status flow is **COMPLETE**:

```
PENDING → PROCESSING → COMPLETED
                    → FAILED (with errorType + errorMessage)
                    → NEEDS_ACCOUNT_SETUP
                    → EMPTY_STATEMENT (subset of FAILED)
```

Error types tracked:
- `PDF_READ_ERROR` — pdf-parse failure
- `AI_PARSE_ERROR` — AI parsing failure
- `CRITICAL_ERROR` — unhandled exception
- `EMPTY_STATEMENT` — no transactions found

Each failure state stores `errorType`, `errorMessage`, and `errorDetails` in the statement record.

## Account Auto-Detection

**Status**: WORKING

Flow:
1. Parser-first: `parserRegistry.detectBank()` → `parser.extractAccountInfo()` (no AI cost)
2. AI fallback: `aiService.extractAccountInfo()` with 2× retry
3. Account matching: SHA-256 hash of account number → `findAccountByHash()`
4. Auto-creation: If no match, creates account with bank name + account type
5. Balance update: Updates account balance from statement closing balance
6. Credit card detection: Separate `detectCreditCard()` for credit limit, minimum payment, business card GST

## Recommendations (Priority Order)

1. **Fix C1 immediately** — statement ID mismatch breaks the entire upload flow
2. **Add file type validation (C2)** — security risk
3. **Add unique constraint on `transactionHash` (C3)** — data integrity
4. **Wire CSV parser into upload pipeline (H1)** — easy win, parser already exists
5. **Add GST fields to agent insertion path (H2)** — BAS accuracy
6. **Fix `parseInt(UUID)` in transfer detection (M5)** — transfer matching is broken
7. **Fix array index mismatch in agent-insertion.ts pending categorization** — silent data corruption
